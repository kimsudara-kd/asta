# Vault feasibility against the exchanges' signing requirements (ASTA-M3B-R4, workstream D)

**No credential was created, imported or requested; synthetic values only; no signing code exists or was activated.** Official sources were read on 2026-11-14 (fetched pages, quoted briefly); anything the pages did not state is marked UNVERIFIED. This document supersedes the unverified product claims of `VAULT-AND-BACKUP.md` s.2-3 where they differ.

## 1. What the exchanges require (verified from the official documentation)
**Binance Spot (REST, `binance-spot-api-docs`):** signed endpoints accept **three key types**: "We support HMAC, RSA, and Ed25519 keys." The signed payload is the query string concatenated with the request body. **HMAC-SHA256**: key = the `secretKey` the exchange issues, output hex. **RSA**: RSASSA-PKCS1-v1_5 with SHA-256, base64 then percent-encoded, PKCS#8 keys, the user *uploads the public key* to get an API key. **Ed25519**: sign the payload, output **base64**; the docs say "It is highly recommended to use Ed25519 API keys"; the user registers the public key. Parameter `signature` (query or body); header `X-MBX-APIKEY` carries the *API key* (a public identifier); `timestamp` required (ms or µs), `recvWindow` default 5000, max 60000; the server rejects if timestamp >= server time + 1 s or older than `recvWindow`. "By default, an API key cannot TRADE": trading must be enabled in key management. `newClientOrderId`: "A unique id among open orders"; "Orders with the same `newClientOrderID` can be accepted only when the previous one is filled" (the doubling hazard U-1 of the order-path design is therefore **documented by Binance itself**).
**OKX (REST v5):** four headers on every private request: `OK-ACCESS-KEY`, `OK-ACCESS-SIGN` (**HMAC SHA256 with the SecretKey over `timestamp + method + requestPath + body`, Base64**), `OK-ACCESS-TIMESTAMP` (ISO-8601 UTC, ms; rejected beyond 30 s, error 50102) and **`OK-ACCESS-PASSPHRASE`: "The passphrase you specified when creating the API key"**, sent in clear (inside TLS) on every request; OKX stores only a salted hash of it. "The SecretKey is generated when you create an API key" (by OKX). Demo trading uses the header `x-simulated-trading: 1` and keys created under *Demo Trading > Personal Center*. Asymmetric keys: the page did not address them (UNVERIFIED).

## 2. The distinction that decides the design: signing-key non-exportability vs API-secret storage
* **Binance with an Ed25519 (or RSA) key is the only case where the secret can be non-exportable end to end:** the key pair is generated **inside the vault**, only the *public* key is registered at the exchange, the private key never exists anywhere else, and the connector asks the vault to sign. Nothing the connector holds can be replayed as a credential: the header carries the API key id, not a secret.
* **Binance HMAC keys and every OKX key are symmetric secrets issued by the exchange.** The secret necessarily exists in plaintext at the exchange and, once, on the operator's screen/clipboard at creation; it must then be **stored and used** by something. "Non-exportable" can only start *after* import, and only if the vault can compute HMAC over an *imported* secret.
* **OKX adds the passphrase**, which is sent in a header: the connector must be able to read it. So for OKX a part of the credential set is *necessarily readable by the connector* regardless of the vault.

## 3. OpenBao against those mechanisms (official OpenBao transit documentation, read 2026-11-14)
| Need | Finding |
|---|---|
| Ed25519 signing inside the vault | supported: `type` list includes ed25519 (sign/verify); `sign` takes `input` base64 and returns `vault:v1:<base64>` (the sample shows standard base64 with `==` padding); **Binance wants the raw base64 signature**: strip the `vault:v1:` prefix and percent-encode (UNVERIFIED byte-for-byte equivalence: must be proven against Binance's published Ed25519 test vector in a rehearsal) |
| Non-exportable keys | `exportable` defaults to **false** and "once set, this cannot be disabled" (i.e. a key made exportable can never be made non-exportable again; keys generated by the engine cannot be re-imported over) |
| HMAC with a vault-generated key | the `hmac` key type exists and `POST /transit/hmac/:name` works with "any type supported by transit" (the pages are slightly inconsistent) |
| **Importing an exchange-issued HMAC secret (OKX; Binance HMAC)** | **the documented import list covers AES, ChaCha20, Ed25519, ECDSA, RSA and ML-DSA; `hmac` is NOT listed.** A vault-generated HMAC key is useless (the exchange must know the secret). So OpenBao transit **cannot hold an exchange-issued HMAC secret as a non-exportable HMAC key** (UNVERIFIED for future versions; test the import endpoint with `type=hmac` in a rehearsal before relying on this) |
| Passphrase / API key id / HMAC secrets | must live in the **KV** engine (readable by an authorised connector role) or a sealed file: not non-exportable |
Conclusion: **OpenBao fits Binance Ed25519 fully, fits nothing of OKX's secrets non-exportably.**

**Decision (recommendation, owner + reviewer approve):** scope the first M3-B to **Binance Spot Testnet with an Ed25519 key in OpenBao transit** (this is also the exchange's own recommendation); keep **OKX out of scope** (consistent with R2: its credentials can only be stored, not made non-exportable, and its demo/production separation is header-based). The fallback for any symmetric secret or the OKX passphrase is the OpenBao KV engine behind a read-only policy for the connector, with the exposure stated honestly: **a compromised connector can read those secrets** (mitigated by egress allowlisting, order caps, kill switch, key restrictions: READ + SPOT TRADE only, IP allowlist to the firewall VM's address, never withdrawal).

## 5. Least-privilege access, backup and recovery
Access: one OpenBao role per venue for the connector, policy = `update` on `transit/sign/binance-testnet-ed25519` and `transit/verify/...` only (+ `read` on `transit/keys/binance-testnet-ed25519` for the public key), no `list`, no `export`, no `kv` access in the Binance-only scope; token TTL ≤ 15 min with renewal by the connector's identity; a separate break-glass admin policy held offline; the operator who unseals is not the connector. Audit: file audit device -> shipped into the ASTA hash chain (`SECURITY-EVENTS-AND-ALERTS.md`); an alert on any `sign` call outside the connector's schedule or any denied request. Backup: OpenBao raft/file storage is **encrypted by the barrier key**; back up the storage with the existing age-encrypted flow; **the transit private key is not exportable, so a restore of the storage plus the unseal shares is the only recovery path**: rehearse it. Loss of the key = register a new public key at the exchange and rotate (testnet keys also vanish on the monthly reset). Unseal shares: 3 shares, threshold 2, held offline by three people/places. Rotation: yearly or on suspicion (a new key version, old versions kept only for verification).
