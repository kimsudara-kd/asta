# VM infrastructure readiness report for independent review (ASTA-M3B-R5, workstream D)

**Design and scratch-environment evidence only. The two-VM boundary does not exist on this Mac; none of this proves deployed host isolation.** Credential-capable services are not provisioned; no exchange credential, signing code or external order path exists.

## 1. Two-VM design against the final resource budget
Guests: `asta-fw` 1 vCPU / 768 MiB / 8 GB and `asta-app` 3 vCPU / 3 GiB / 40 GB (`qemu-vms.sh` specs, tested); the credential VM (1 vCPU / 1 GiB / 10 GB) refuses to start until M3-B is authorised (`ASTA_ENABLE_CRED=1` is the later phase). RAM: ~3.84 GiB of guests + ~0.3 GiB QEMU overhead; measured under combined load on today's contended host without failure (`CAPACITY-ASSESSMENT.md`). **Storage (actual, 2026-11-14): the internal APFS container has 59.3 GB unallocated (24.2 %), Data volume 57 GiB free.** The budget needs a 60 GiB quota plus a 25-30 GiB macOS reserve, so **VM provisioning must wait until the unrelated Docker data (50.6 GiB `Docker.raw`) has left or a separate APFS volume exists**; the check is repeatable with `diskutil apfs list` and `df -g` and is a precondition in the execution plan.

## 2. QEMU binary and dependency integrity
Pin of 31 files (binary, two EFI firmware files, the Homebrew dylib closure) verified **again today: all match** (`qemu_pin.py verify`); installed QEMU 11.1.3 from the Homebrew core bottle `arm64_tahoe` (the bottle SHA-256 is recorded in `qemu-pin.json`; the installed binary is ad-hoc re-signed with the hypervisor entitlement, so only the pin ties it to this host). `qemu-vms.sh run` refuses to start a VM without a matching root-owned pin (exit 70, tested: refusal precedes any QEMU launch). The pin is a draft generated by me; the owner regenerates it at provisioning after `brew fetch --bottle-tag arm64_tahoe qemu`.

## 3. Runtime-VM route, DNS, IPv4/IPv6, direct-IP and proxy-bypass denial
Executed in a scratch aarch64 Linux 6.8 kernel with the **unmodified** nftables files (`docs/evidence/m3a/r4-netns-lab-aarch64.json`, **38/38**): only `lo` + the one firewall link on the app side; no global IPv6; IPv6 to public resolvers and to the firewall's link-local address blocked; direct-IP 443/80, DNS over UDP/TCP 53, DoT 853, QUIC blocked; cloud metadata, RFC1918 and CGNAT ranges blocked; extra on-link /32, low-metric default route and a policy rule open nothing; with the app's own firewall flushed the firewall VM still blocks; with the firewall VM gone there is no connectivity. Static device tests: the app VM has exactly one NIC (unix-socket stream to the firewall VM), and no VM has a host-network, share, USB, VNC or forwarding device. **Not covered:** the real QEMU `stream` links, `socket_vmnet`, the hypervisor boundary, the real proxy and allowlist, host `pf`/application firewall, capture on `en0`.
