# Vault backend recommendation and backup-key ceremony (ASTA-M3B-R3, workstream C)

**No exchange credential was created, imported or requested.** The mock vault (`security/vault.py`) is unchanged except that it now refuses non-synthetic values (M3-B-R2). Statements about third-party products below come from the implementer's knowledge, **not from a download or a live check**; every availability, licence and artifact claim must be verified against the upstream release (version, checksum, signature) at provisioning, on a host with the owner's approval. They are marked UNVERIFIED.

## 1. Requirements the backend must meet
R1 runs on **Linux aarch64** inside `asta-cred` (no Internet in the VM; artifact delivered on the read-only payload disk); R2 the private key/secret is **never readable by the connector** (best: signing happens inside the vault); R3 encryption at rest independent of the host disk (FileVault is off today); R4 an **audit log** that cannot be edited by the connector and can be shipped into the ASTA audit chain (F-07); R5 policy-based access: connector identity only, short-lived leases, no human bulk-read; R6 **revocation and rotation**; R7 fail closed when sealed/unavailable; R8 small footprint (cred VM <= 1 GiB); R9 reviewable by an independent party; R10 no dependency on a cloud service.

## 3. Recommendation: **OpenBao in `asta-cred`, transit engine, Ed25519, sign-only policy**
Documented security assumptions: (1) the demo key is an **Ed25519 key pair generated inside OpenBao**; only the public key leaves it and is registered by the owner at the exchange (READ + SPOT TRADE only, never withdrawal/transfer); the private key is never exported, so no plaintext key exists anywhere, which also removes the "move the secret into the vault" ceremony; (2) the connector authenticates with a role that may call **only** `transit/sign/<key>` and `transit/verify` and read nothing else; (3) unseal shares: 2-of-3 Shamir, held offline by the owner and two further custodians (or two offline media + a paper copy); initial root token revoked after setup; (4) audit device writes to a file readable by a log shipper, not by the connector; (5) swap disabled and memory locked in `asta-cred`; (6) the VM disk is on an APFS volume (FileVault recommended); (7) the unix socket / loopback listener only, no network; (8) policy changes need the existing two-reviewer signed configuration (`verify_privilege_config`, F-06) plus a documented procedure; (9) **residual:** a compromised connector can still *request signatures* while it runs (mitigated by the pre-trade guard, per-order caps, kill switch, gateway) - the vault limits key theft, not misuse during compromise; (10) restart needs a human to unseal: the order path stays closed (acceptable and intended). If an independent reviewer prefers lower complexity, the fallback is age + systemd-creds with the documented loss of R2/R4/R5. Decision owner: CEO + independent reviewer (F-05/F-06). Nothing is installed.

## 4. Backup private-key relocation ceremony (owner procedure; not performed)
Facts: the committed recipient is `infra/security-host/mac/backup-recipient.pub`; the matching identity is **on this Mac's unencrypted SSD** (`~/asta-backup-identity/identity.txt`, 0600) and SSDs cannot be securely erased, so the key must be treated as **exposed to anyone with disk access**. **No real backup has been encrypted to it yet**, therefore the recommended ceremony is to **replace the key pair rather than relocate it**:
1. Prepare **two offline media** (small USB sticks, any filesystem; the 4 TB exFAT backup SSD is permanently attached and is *not* offline) kept in different physical places, plus an optional paper copy of the identity (about 190 characters).
2. Insert media A. Generate the new pair **directly on the media**: `age-keygen -o /Volumes/KEYA/asta-backup-identity.txt` (the identity never touches the Mac's disk); write the printed recipient to the clipboard/paper.
3. Copy the identity to media B and verify both byte-for-byte (`shasum -a 256`); eject; store separately.
4. Commit only the new **public** recipient as `backup-recipient.pub` (replace the old one in a reviewed commit) and place it on `asta-app` at `/etc/asta/backup-recipient.pub`.
5. Retire the old pair: delete `~/asta-backup-identity/` (acknowledging that flash may retain remnants: hence the replacement) and record the old recipient as revoked.
6. **Verify:** run the rehearsal (`backup-key-rehearsal.sh`) for the procedure; then create a first *synthetic* encrypted dump on the VM and restore it with media A on a scratch VM (`db_restore_verify.sh`); only then the key is considered live.
7. Custody and schedule: restore drill every 90 days with alternating media; key rotation yearly or on any suspicion; a custody log entry for each access to the media; if both media are lost, backups are unrecoverable (rebuild from the live database and rotate).
8. Never put the identity in the repository, a chat, a cloud folder, the VM, or any online backup.

## 5. Synthetic-key-only recovery rehearsal (executed)
`infra/security-host/mac/backup-key-rehearsal.sh` (stdlib shell + `age`): a throw-away key pair in a private temp directory; encrypts a synthetic dump with the recipient only; moves the identity to simulated "offline media" and removes it from the simulated "host"; shows the host can still back up but cannot decrypt, a restore with the offline identity gives an identical checksum, a different identity cannot decrypt, the ciphertext contains no plaintext marker, a corrupted backup is detected, and the temp directory is removed. **Result (macOS arm64, age 1.3.2): all 8 checks passed** (`docs/evidence/m3a/r3-backup-key-rehearsal-macos.json`); a test asserts the script never references the real identity and that the real identity file's metadata is unchanged. This rehearses the *procedure*; it does not prove the real media, custody or the VM-side restore.

## 6. Credential access controls and audit requirements (for the future, M3-B)
Access: one connector identity per venue (`vault/binance/spot-testnet`, OKX excluded); permissions READ + SPOT_TRADE only (the mock vault already refuses others and now refuses non-synthetic values; the real backend must refuse withdrawal-capable keys, verified against the exchange's key-permission response at start-up); leases <= 60 s; no human read path; strategies, AI modules, UI and operators are refused. Audit: every grant, lease, refusal, policy change, unseal, rotation and revocation is logged with who/what/when and **never secret material**; the vault audit device and the proxy log are shipped into the hash-chained ASTA audit (F-07) and checked by the monitor (alert on any lease outside the connector's schedule, any refusal burst, any policy change, any unseal); rotation every 30 days (the existing contract's default TTL) and immediately on suspicion; revocation destroys the key material and is rehearsed. Reviewer evidence required: the written policy set, the audit sample, a rotation + revocation drill, an unseal drill, proof the connector cannot read the key.
