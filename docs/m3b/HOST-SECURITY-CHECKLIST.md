## 2. FileVault activation with recovery-key escrow (prepared)
What it protects and what it costs: the SSD is hardware-encrypted on Apple silicon at all times, but with FileVault off the key is released without a password, so a stolen or copied machine is readable. FileVault binds the key to the user password. Costs: (1) **after any reboot (power loss included) the Mac waits at the pre-boot login screen until a human types the password**, so the VMs and bridge do not start unattended (the order path stays closed meanwhile: the safe direction); a *planned* restart can skip one prompt with `sudo fdesetup authrestart`; (2) automatic login is disabled; (3) SSH-based unlock after power loss is not available on Apple silicon. This conflicts with unattended 24/7 paper observation: **decision D-F: FileVault before any credential exists (recommended), accepting manual unlock after power events.**
Window procedure: 1) verify backups; 2) confirm the admin user has a Secure Token (`sysadminctl -secureTokenStatus apple`); 3) turn FileVault on in System Settings > Privacy & Security (or `sudo fdesetup enable`), choose **a personal recovery key and not iCloud recovery** (no account-linked escrow, no Apple ID dependency); 4) the **recovery key is shown once**: write it on paper by hand, check every character, make **two copies** stored in two physically separate places (a safe and a second location); never photograph it, put it in the repo, a chat, a cloud folder or a password manager that syncs to the same Apple ID; 5) wait for encryption to finish (`fdesetup status`: "Encryption in progress" -> "FileVault is On"); 6) **test the recovery key** in the same window on a restart if you accept the risk (or at the next planned reboot with someone ready); 7) record the date and who holds the copies in a custody log (not in git). Rollback: `sudo fdesetup disable` (decrypts in the background; takes hours; the Mac stays usable). Open question for the owner: how power loss will be handled while you are away (UPS, someone to unlock).

## 3. Controlled application-firewall activation (prepared)
The macOS application firewall filters inbound connections per application, **not per port**: it is defence in depth only; the boundary is the firewall VM. Plan: 1) **resolve D-A first** (unrelated listeners are what it would break: `EXO`, Docker-published ports, SSH/SMB); 2) list what must accept inbound after the change (the ASTA dev stack and the Docker boundary are loopback-only and need none; `tailscaled` handles its own interface; SSH only if D-B3 keeps it); 3) `sudo /usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate`; 4) `--setglobalstate on`, **then** `--setblockall off` (do not use block-all while Tailscale/SSH are needed), `--setallowsigned on` (signed system software only), `--setallowsignedapp off`; 5) add explicit allowances only for the identified binaries (`--add`, `--unblockapp`); 6) enable stealth mode last (`--setstealthmode on`); 7) verify: `host-separation-check.sh` (listener checks), the dashboard over the tailnet, SSH from an allowed client, ASTA tests unchanged; 8) rollback = `--setglobalstate off`. provision-host.sh's `--firewall` flag does steps 4 and 6 only; it is separate from the VM provisioning so each can be rolled back on its own.

## 6. QEMU pin and trusted installation source (done offline; installed only by provisioning)
Source: Homebrew core formula `qemu` 11.1.3, bottle `arm64_tahoe` (GHCR), formula bottle SHA-256 `40e8e019...104fdf` (full value in `qemu-pin.json`), installed from the bottle (receipt: `poured_from_bottle`), signed **ad hoc** with the `com.apple.security.hypervisor` entitlement (Homebrew re-signs after relocation, so the installed hash is host-specific and not comparable with the bottle). `infra/security-host/mac/qemu_pin.py generate` pinned **31 files**: the binary (`2280d705...662098a1`), the two EFI firmware files and every Homebrew dylib in the binary's dependency closure (`otool -L`, recursive; system libraries are covered by SIP). `qemu-pin.sha256` (checked with `shasum -a 256 -c`) is installed root-owned by `provision-host.sh` (it refuses to proceed if the pin does not match the installed QEMU) and **`qemu-vms.sh run` refuses to start any VM unless the pin verifies** (exit 70, fail closed; tests prove the refusal happens before any QEMU process). To verify the source independently before provisioning: `brew fetch --bottle-tag arm64_tahoe qemu` (re-checks the bottle SHA-256) and compare with `qemu-pin.json`; optionally `brew verify qemu` (attestations). Residual: the pin is generated *by me on this host*; **the owner must regenerate it at provisioning** after the bottle check, and any `brew upgrade` of QEMU or its libraries deliberately invalidates it (re-pin after re-verifying).
