## 3. Topology (Phase B): three Linux ARM64 VMs on QEMU + Hypervisor.framework
```
 Mac mini M4 (macOS host, dedicated to ASTA; no other use; Wi-Fi/Bluetooth/sharing off)
  Ethernet en0 ──(root socket_vmnet, bridged, group-restricted unix socket)──► asta-fw  up0 (the ONLY uplink)
                                                                                  │ app0 (unix-socket L2 link, 10.77.1.0/30)      │ cred0 (10.77.2.0/30)
                                                                                  ▼                                               ▼
        asta-app: paper service, supervisor, API, PostgreSQL (unix socket),    asta-cred: vault + (future) connector ONLY
        backups. NEVER holds credentials. 3 vCPU / 5 GB / 60 GB                1 vCPU / 2 GB / 10 GB
        (app <-> cred link 10.77.3.0/30 exists in the design but is NOT attached until M3-B is authorized)
        asta-fw: nftables + proxy, never forwards. 1 vCPU / 1 GB / 8 GB
```
**Why three VMs:** the strongest form of F-01 - the credential-bearing machine contains nothing else, and the application machine (the descendant of today's legacy Windows processes) has no route to it and no vault code. The firewall VM never forwards, so app and cred cannot talk to each other through it.
**Why QEMU+HVF and unix-socket links:** the links exist nowhere on the host network (no vmnet interface, no host address, no bridge); the socket directory is mode 0700 owned by an unprivileged `_astavm` user, so only that user's QEMU processes can attach. Apple Virtualization.framework front ends (Tart, Lima-vz, UTM-AVF) provide only NAT/bridged/host-only vmnet networks that give the macOS host an address on the guest segment, so they are not used for the isolated links. VMware Fusion/Parallels could offer private switches but are commercial and less scriptable; VirtualBox on Apple Silicon is limited. QEMU needs a **separate, authorized provisioning step** (Homebrew install, an unprivileged service user, a root `socket_vmnet` helper for the bridged uplink).
**Resources (16 GB / 256 GB):** VMs total 5 vCPU / 8 GB RAM / 78 GB disk (thin qcow2) + 20 GB backup disk; leaves about 8 GB RAM for macOS and ~150 GB free (the observation database dump is about 0.9 MB after one day). An **external drive is required for backups** (the internal SSD is too small to be its own backup).

## 4. Independently enforced egress and the approved destinations
Same policy as the verified Docker gate and the dedicated-host design, per VM (`infra/security-host/mac/*/nftables.conf`, all `nft -c`-validated): default DROP in every hook (IPv6 only loopback); **asta-fw** input only from `app0`/`cred0` to TCP 3128, forward DROP, output only TCP 443/9443 to addresses resolved from the allowlisted names (public IPv4 only, refreshed every 60 s by a root job; the proxy user has no DNS egress and resolves from a hosts file) plus root-only DNS/NTP to one pinned upstream; **asta-app** output only `10.77.1.1:3128`; **asta-cred** output only `10.77.2.1:3128`; neither accepts any inbound connection (administration is the host-local console socket, not SSH). Approved public destinations (`infra/egress/allowlist.json`, runtime profile): `data-api.binance.vision`, `data-stream.binance.vision`, `www.okx.com`, `ws.okx.com` (public market data only). Binance testnet hosts exist only in the reviewed `capability_probe` profile and are not enabled for operation. Units add `IPAddressDeny=any` with explicit allows as a third layer.

## 5. Runtime, PostgreSQL, supervision, vault isolation
* **Runtime delivery (no Internet on the VM):** `build_seed.py --target=mac` writes reproducible cloud-init seeds for `fw`, `app`, `cred` (no key or secret embedded; operator SSH public-key placeholder; the application secret key and the backup recipient public key are created/placed on the VM at provisioning). The ASTA source and the 36 aarch64 wheels arrive on a **read-only payload disk** built on a trusted machine (`uv export --frozen --no-dev` + `pip download --platform manylinux2014_aarch64`, hashes in the evidence file) and are installed into `/opt/asta/venv` offline.
* **PostgreSQL 16 (apt, ARM64) on asta-app:** `listen_addresses = ''` (no TCP listener), peer authentication only (`pg_hba.conf.asta`: role `asta` <- OS user `asta-app`, every `host` line rejects) - **no database password exists**; the application URL uses the unix socket.
* **Supervision and recovery:** `asta-paper-supervisor.service` (`Restart=always`, runs `paper_supervisor_posix.py`) and `asta-paper-service.service`, both as `asta-app`, hardened (`NoNewPrivileges`, `ProtectSystem=strict`, empty capability set, syscall filter, `IPAddressDeny=any` + proxy and loopback only, `HTTPS_PROXY` fixed). Health samples keep going to `supervisor.jsonl`, so coverage/availability are measured exactly as on Windows.
* **Vault isolation:** vault and connector units from the dedicated-host design live only on `asta-cred` (vault: `PrivateNetwork=yes`, unix socket, group `asta-connector`); not installed or enabled now (M3-B modules do not exist). The macOS host holds no secret: no credentials, no vault key, no unlock secret (the KEK is supplied by the operator at the VM console or as a TPM-less encrypted credential, decided with the reviewer).

## 6. Database backup and restoration
`asta-db-backup.timer` (daily 02:30 UTC) runs `db_backup.sh` on asta-app: `pg_dump -Fc | age -R <offline recipient public key>`, written to a dedicated 20 GB raw disk (`asta-backup.img`) that holds **only age-encrypted dumps**; the host copies that image to the external drive during a maintenance window (the host cannot read ext4 and never sees plaintext); retention 14 dailies. **Restore drill** (`db_restore_verify.sh`): decrypt with the offline private key (never on any VM except during the drill, at the console) into a scratch database and run `paper_integrity.py` (ids, config hashes, checkpoint replay, reconciliation); never touches the live database. A dump is architecture-independent (`pg_dump -Fc`), so a dump from the Windows database restores on ARM64 and vice versa. Also image-level snapshots of VM disks before every change. Time-to-restore target: under 30 minutes for the database (dump about 0.9 MB today).

## 7. Logs, monitoring, host reboot recovery
* **Logs and monitoring:** journald in each VM; nftables drop counters and the proxy JSON decision log (to be shipped to the audit chain - F-07); host-side launchd logs in `/var/log/asta/`; alerts listed in `VM-BOUNDARY-DESIGN.md` R2-4 (DENY bursts, `resolves-to-non-public`, policy change, allowlist set empty, refresh failure, unit failure, clock drift, vault lease anomalies, disk > 80 %).
* **Host reboot recovery:** LaunchDaemons (`com.asta.socket_vmnet`, `com.asta.vm.{fw,app,cred}`) start at boot **without a login**, restart on failure (`KeepAlive`), VMs reconnect their links automatically (`reconnect-ms`), guests start their services via systemd, the supervisor reconciles before resuming and records the gap as unmonitored time. Required macOS settings (applied only at provisioning, not now): `pmset` auto-restart after power failure, no system sleep or disk sleep, wake-on-network off, a UPS. **FileVault decision (CEO/reviewer):** with FileVault on, the Mac stops at the pre-boot unlock screen after a power loss and nothing starts until someone enters the password (planned reboots can use `fdesetup authrestart`); with FileVault off, recovery is automatic but disk contents (VM disks with the encrypted vault store and encrypted backups, no plaintext secrets by design) are unencrypted at rest. Recommendation: FileVault ON if the Mac is attended; otherwise OFF **only because** no secret ever lives on the host and the vault and backups are encrypted by their own keys. Reboot acceptance is `vm_acceptance.py ... pre` / `post --pre` per VM (boot_id changed, identical ruleset hash and routes, same services) plus the host-reboot matrix, **not yet run**.
* **Rollback to the existing Windows environment:** Windows stays authoritative until a separately authorized cutover; the M2 sessions, supervisor and database are untouched. After a cutover, rollback = stop `asta-paper-*` on asta-app, take a final encrypted dump, restore it into the Windows `asta-db` (`pg_restore`), verify with `scripts/m2_migration_rehearsal.py`-style integrity, restart the Task Scheduler supervisor; disclose the gap as unmonitored time. Disk snapshots give the second path on the Mac.

## 8. Adapted or replaced x86-only / Windows-only items
`hyperv-create.ps1`, `virtualbox-create.sh`, `libvirt-create.sh` (earlier hypervisor scripts) are **not used** for the Mac; replaced by `mac/qemu-vms.sh` + `mac/launchd/*.plist`. Cloud-init seeds, nftables, netplan, systemd units, the proxy, the acceptance and vault-validation scripts are architecture-independent (Python/shell/nft). The Windows-only supervisor helpers got a POSIX entry point; browser/e2e tooling got ARM64-safe switches (Windows behaviour unchanged, regression re-run).

## 9. Phase C - isolated validation plan (after separate provisioning authorization)
1 Provision `_astavm`, QEMU, `socket_vmnet`, the three VMs from the seeds, on the Mac (changes require the owner's approval and are listed in section 10). 2 Install the runtime from the payload; run the full ASTA suite on a **scratch** VM with a local Postgres test instance (`ASTA_TEST_DATABASE_URL`) and Chromium (`E2E_BROWSER_CHANNEL=chromium`) - not on the production app VM. 3 Run `negative_tests.py` (78 checks, `ASTA_PROXY=10.77.1.1:3128`) from asta-app and asta-cred, and the compromised-proxy checks (`vm_acceptance.py firewall`) on asta-fw. 4 Verify ASTA's real REST/WS clients through the proxy on ARM64. 5 Reboot matrix: guest reboot, VM restart, host reboot, power loss, snapshot revert (`vm_acceptance.py` pre/post, fail-closed with asta-fw stopped). 6 `vault_validation.py` (synthetic secrets) on asta-cred. 7 Restore a copy of the M2 database (the encrypted dump route) on asta-app. 8 Replay every checkpoint on ARM64 and reconcile ledgers (**cross-architecture determinism**); compare with the Windows source. 9 Run restored **test** sessions on the copy (observation-only), never the originals. 10 Hand the evidence to the independent reviewer. Until each step has run, **F-01/F-02 stay OPEN**; a Mac host reduces but does not remove the shared-host trust (a compromise of macOS administrator rights defeats the VM boundaries), which the reviewer must weigh (finding F-19 in the register).
